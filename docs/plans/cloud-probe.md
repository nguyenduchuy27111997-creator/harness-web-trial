## What the loop would need to change to run here

1. **Start Docker itself.** No daemon is running at session start. Something like `pgrep dockerd || (dockerd >/var/log/dockerd.log 2>&1 &)` is needed before `db-up.sh` (in the environment's setup script or in `init.sh`). `db-up.sh` already fails fast with "Docker is not running".
2. **Node 26.** Install the `.nvmrc` version in the environment's setup script (`nodejs.org` is reachable). Otherwise `npm ci` fails, and with it `check.sh`'s reinstall step, which every fresh worktree or lane hits.
3. **Network allow-list** (environment settings → Allowed domains), at least:
   - `semgrep.dev`: the `sast.sh` rule registry (or vendor the rules / run Semgrep only in CI);
   - `cdn.playwright.dev` (and `playwright.download.prss.microsoft.com`): only if a local `playwright install` is wanted. The gate does not need it.
4. **Proxy CA in the browser container.** `scripts/browser.sh` (a protected file) should pass the CA when it exists: `-v /root/.ccr/ca-bundle.crt:/tmp/ca.crt:ro -e NODE_EXTRA_CA_CERTS=/tmp/ca.crt`. Better still, bake the `playwright` package into the image so it needs no `npx -y` download. The same applies to any other container that fetches over HTTPS.
5. **GitHub: replace every GraphQL-backed `gh` call with `gh api` REST.** `harness/github.py`, `merge.py`, `stages.py`, `scheduler.py` and `loop.py` use `gh pr create/view/edit/merge/close/checks/list/comment`, `gh issue list/comment` and `gh repo view`, and all of these hit GraphQL. Their REST equivalents:
   - `pr create` → `POST repos/{r}/pulls`; `pr view --json` → `GET repos/{r}/pulls/{n}` (`head.sha`, `merge_commit_sha`); `pr edit --base/--body-file` → `PATCH repos/{r}/pulls/{n}`;
   - `pr merge --squash --match-head-commit` → `PUT repos/{r}/pulls/{n}/merge` with `merge_method=squash, sha=…`; `pr close` → `PATCH … state=closed`; `pr list --head` → `GET repos/{r}/pulls?head={owner}:{branch}&state=open`;
   - `pr checks` → `GET repos/{r}/commits/{sha}/check-runs`; `pr/issue comment` → `POST repos/{r}/issues/{n}/comments`; `issue list --label --search` → `GET repos/{r}/issues?labels=harness&state=open` (filtered locally) or `GET search/issues`;
   - `repo view --json nameWithOwner` → `git remote get-url origin` or `gh api repos/{r}`;
   - auto-merge and ready-for-review, if used: the proxy's `/pulls/{n}/ccr/...` routes.
   - `gh run list/view/rerun/cancel` and `gh api` already work (REST).
6. **Session lifetime.** The loop must expect pauses when idle and a container reclaimed after inactivity. Everything worth keeping (state in `harness/status`, logs, worktrees) has to be pushed or survive a restart, and Docker, Supabase and the browser container must come back up on resume. Running for days unattended is not demonstrated here.
7. **Capacity.** 4 vCPU / 15 GB: the warm e2e suite took about 23 min on one worker. That is too slow for several lanes, each running e2e. Plan on 1–2 lanes with `HARNESS_E2E=feature`, and leave the full suite to CI.
8. **Nested `claude` sessions work** with no API key, through the session's own auth. Check that the loop does not set `ANTHROPIC_API_KEY` or a model the account cannot use. Usage is billed to this account.

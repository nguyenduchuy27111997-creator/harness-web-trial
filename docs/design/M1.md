# Design M1: email/password accounts and a private shelf (list and add books)

## Features
- F001 Sign up: `signUp` action, credential validation (`lib/auth.ts`), server Supabase client with cookie sessions, header with Sign out.
- F002 Sign in / sign out: `signIn`, `signOut` actions; generic "Invalid email or password".
- F003 Redirects: `proxy.ts` session refresh and `/books*` guard, `requireUser()` (`lib/supabase/server.ts`) in pages, `/` redirects to `/books`.
- F004 Empty shelf: the `books` migration and generated types, `listBooks` returning `[]`; `/books` empty state linking to `/books/new`.
- F005 Add a book: `createBook` action, `insertBook`, `parseNewBook`, status select defaulting to `want_to_read`.
- F006 Validation: `parseNewBook` field errors shown next to each field; the table's checks back them up.
- F007 List order and badges: `listBooks` ordered `created_at desc`; `STATUS_LABELS`; titles in `font-serif`.
- F008 Isolation: RLS on `books` (owner only); `user_id` set by the database, never by the form.
- F017 Signed-in users leave the auth pages: `proxy.ts` redirects a signed-in user requesting `/sign-in` or `/sign-up` to `/books` (decision 0004); no migration, no new contract.

## Data model
Auth users live in Supabase's `auth.users` (email + password, no confirmation: `enable_confirmations = false`, `minimum_password_length = 6` in `supabase/config.toml`, already set). No profile table.

`public.books`
| column | type | rules |
|---|---|---|
| `id` | `uuid` | primary key, `default gen_random_uuid()` |
| `user_id` | `uuid` | `not null`, `default auth.uid()`, `references auth.users(id) on delete cascade` |
| `title` | `text` | `not null`, `check (char_length(title) between 1 and 200)` |
| `author` | `text` | `not null`, `check (char_length(author) between 1 and 120)` |
| `status` | `text` | `not null`, `default 'want_to_read'`, `check (status in ('want_to_read','reading','finished'))` |
| `created_at` | `timestamptz` | `not null`, `default now()` |

- Index: `books_user_id_created_at_idx on books (user_id, created_at desc)`: the only query in M1 is "my books, newest first".
- RLS enabled. Policies, `to authenticated`, both on `(select auth.uid()) = user_id`:
  - `books_select_own` for `select` (`using`)
  - `books_insert_own` for `insert` (`with check`)
- No update or delete policy in M1 (no feature needs them); M2 adds them with its own migration. `anon` has no policy, so it reads and writes nothing.
- M2 columns (finish date, rating, review) are not added now.

### Migrations
1. `supabase/migrations/<timestamp>_create_books.sql` (F004): create `books` with the columns, checks and index above, `alter table books enable row level security`, the two policies. `-- rollback: drop table public.books;`. Then `npm run db:types` and commit `lib/database.types.ts`.

No other schema change in M1. F004 owns this migration because it is the first feature that reads `books` (F005 depends on F004); F005 to F008 reuse it and add none. F001 to F003 need no migration.

## Contract
All types live in `lib/` and are built on `lib/database.types.ts`. Server actions are used with `useActionState`, take `(prev: State, formData: FormData)` and return the state; on success they `redirect()` instead of returning.

Shared shapes (`lib/forms.ts`):
```ts
type FieldErrors<K extends string> = Partial<Record<K, string>>;
type FormState<K extends string> = { fieldErrors?: FieldErrors<K>; formError?: string; values?: Partial<Record<K, string>> };
type Parsed<T, K extends string> = { ok: true; value: T } | { ok: false; fieldErrors: FieldErrors<K> };
```

Auth (`lib/auth.ts`, pure, unit-tested):
- `parseSignUp(formData): Parsed<{ email: string; password: string }, "email" | "password">`. Email trimmed; errors "Email is required", "Enter a valid email" (must contain one `@` with text on both sides), "Password must be at least 6 characters".
- `parseSignIn(formData)`: same shape, but checks only that both fields are present ("Email is required", "Password is required"); no length or format rule, so a wrong short password still gets "Invalid email or password".
- `type AuthFormState = FormState<"email" | "password">` (`values` never holds the password).

Server actions, `app/(auth)/actions.ts`:
- `signUp(prev, formData): Promise<AuthFormState>`: `parseSignUp`; `supabase.auth.signUp`. Error code `user_already_exists` (or a returned user with no identities) → `formError: "An account with this email already exists"`; any other error → `formError: "Could not sign up. Try again."`. Success → `redirect("/books")` (signed in at once).
- `signIn(prev, formData): Promise<AuthFormState>`: `parseSignIn` (empty fields give field errors); `signInWithPassword`; any auth error → `formError: "Invalid email or password"`. Success → `redirect("/books")`.
- `signOut(): Promise<void>`: `supabase.auth.signOut()`, `redirect("/sign-in")`. Called from a `<form action={signOut}>` in the header.

Books (`lib/books.ts`, unit-tested; `listBooks` and `insertBook` take the client as a parameter and are tested with a stub `SupabaseClient`):
- `BOOK_STATUSES = ["want_to_read", "reading", "finished"] as const`; `type BookStatus` (equal to the generated column type narrowed by this list); `STATUS_LABELS: Record<BookStatus, string>` = Want to read, Reading, Finished.
- `type Book = Pick<Tables<"books">, "id" | "title" | "author" | "status" | "created_at">` with `status: BookStatus`.
- `parseNewBook(formData): Parsed<{ title: string; author: string; status: BookStatus }, "title" | "author" | "status">`. Title and author trimmed; errors "Title is required", "Title must be at most 200 characters", "Author is required", "Author must be at most 120 characters"; an unknown status → "Choose a status"; a missing status → `want_to_read`.
- `listBooks(supabase): Promise<Book[]>`: select own books (RLS filters), `order("created_at", { ascending: false })`. Throws on a database error (the error boundary shows it).
- `insertBook(supabase, input): Promise<void>`: insert `{ title, author, status }` without `user_id` (the default fills it). Throws on error.
- `type BookFormState = FormState<"title" | "author" | "status">`.

Server action, `app/books/actions.ts`:
- `createBook(prev, formData): Promise<BookFormState>`: `requireUser()`; parse; on errors return `{ fieldErrors, values }`; else `insertBook`, `revalidatePath("/books")`, `redirect("/books")`. A database error returns `formError: "Could not save the book. Try again."`.

Supabase clients (`lib/supabase/`):
- `server.ts`: `createClient()`: `createServerClient` from `@supabase/ssr` with Next's `cookies()`, typed `SupabaseClient<Database>`, reading `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`. The only way server code gets a client. No service-role key in app code.
- `server.ts`: `requireUser(): Promise<User>`: `getUser()` on the server; `redirect("/sign-in")` when there is none.
- `proxy.ts`: `updateSession(request): Promise<{ response: NextResponse; user: User | null }>`: refreshes the session cookies.

Routes (`app/`):
| route | access | does |
|---|---|---|
| `/` | any | `redirect("/books")` |
| `/sign-up`, `/sign-in` | signed out (a signed-in user is redirected to `/books` by `proxy.ts`, decision 0004) | form, client component with `useActionState`; link to each other |
| `/books` | signed in | `requireUser()`, `listBooks`; heading "My books"; empty state (one sentence + "Add book" link-button to `/books/new`) or the list; "Add book" also shown above a non-empty list |
| `/books/new` | signed in | form: Title, Author (inputs), Status (shadcn `Select`, default Want to read), Save |

`proxy.ts` (root, Next 16's replacement for `middleware.ts`): calls `updateSession`; when the path starts with `/books` and there is no user, redirects to `/sign-in`; when the path is `/sign-in` or `/sign-up` and there is a user, redirects to `/books` (decision 0004). Matcher excludes `_next/static`, `_next/image`, `favicon.ico`, `/api/harness-health`. The proxy is a convenience; `requireUser()` in each protected page and RLS are the real guards.

Header (`components/site-header.tsx`): app name linking to `/books`; when signed in, a Sign out button (form posting to `signOut`, passed in as a prop from the layout so `components/` does not import `app/`). Rendered by `app/layout.tsx`, which reads the user with `getUser()`.

## Modules
| folder | one job |
|---|---|
| `app/` | routes, layouts and server actions: thin, they parse via `lib/`, call `lib/`, redirect |
| `components/` | presentational UI (`components/ui/` shadcn bases, plus app components like `site-header`, `book-list`, `status-badge`, form pieces) |
| `lib/` | types, validation, data access and Supabase clients |
| `lib/supabase/` | the only place that constructs a Supabase client; also `requireUser()` |
| `proxy.ts` | session refresh and the signed-in/signed-out redirects (outside the dependency-cruiser scope; imports only `lib/supabase/proxy.ts`) |

Import rules (each is a `forbidden` rule in `.dependency-cruiser.cjs`):
- `lib/` must not import `app/` or `components/`.
- `components/` must not import `app/`.
- `components/` must not import `lib/supabase/` or `@supabase/*`: UI gets data as props and actions as props; it never talks to the database. (It may import types, labels and `utils` from `lib/`.)
- `@supabase/ssr` is imported only by `lib/supabase/`.
- No cycles.

## NFR
- Load: a personal app: tens of users, each with up to a few hundred books (well under 10k rows). `/books` loads every book of the user in one indexed query, no pagination in M1. Pages meet the existing Lighthouse budgets (performance and accessibility ≥ 0.9, LCP ≤ 2.5 s, ≤ 500 KB); add `/sign-in` and `/sign-up` to `pages` in `lighthouserc.cjs` (the `/books` pages need a session, so they are covered by e2e only).
- Security: threats are another user reading or adding to my shelf, an anonymous visitor reading any shelf, and forged ownership. RLS on `books` allows only `authenticated` users to select or insert rows where `user_id = auth.uid()`; `user_id` comes from the database default, and the insert policy's `with check` rejects any other value. The browser holds only the anon key and the user's session cookie (httpOnly handled by `@supabase/ssr`); the service-role key is never used by app code. Inputs are validated server side in `parseSignUp`/`parseSignIn`/`parseNewBook`, and the table's checks repeat the length and status rules. Sign-in errors do not reveal whether an email exists. React escapes titles and authors on render; no `dangerouslySetInnerHTML`. Server actions get Next's built-in origin check against CSRF.
- Cost: none beyond local Docker for development; staging uses a Supabase preview branch and a Vercel preview on the free tiers. No paid service.

## Decisions
- **`@supabase/ssr` cookie sessions with server actions** (F001 adds the pinned dependency). Rejected: a browser-only Supabase client, because `/books` must be server-rendered for the signed-out redirect and RLS-scoped reads, and client-side tokens would need a separate guard.
- **Hand-written validation in `lib/`** instead of adding zod: four fields with length rules do not justify a dependency, and the parsers are pure and unit-tested.
- **`status` as `text` with a check constraint**, not a Postgres enum: the same safety, and changing the allowed values later is a plain migration without `alter type`.
- **`user_id` filled by `default auth.uid()`**, not sent by the app: the form cannot forge ownership, and the insert policy still checks it.
- **Only select and insert policies in M1**: no M1 feature updates or deletes, so the narrower grant ships first; M2 adds update and delete policies with its features.
- **Guard in three layers** (proxy redirect, `requireUser()` in pages and actions, RLS): the proxy alone is not a security boundary in Next 16.
- **Testing `lib/`**: pure parsers and `lib/books.ts` are unit-tested (stub client); `lib/supabase/**` (client construction, cookies, `requireUser`) is excluded from coverage in `vitest.config.ts` and covered by e2e, since unit-testing it means mocking Next's `cookies()` and `@supabase/ssr` and proves little. Coverage thresholds stay as they are. Rejected: mocking Next and Supabase internals to reach 80% there.
- **Separate sign-in and sign-up parsers**: sign-in must not reveal the password rule or answer differently for short passwords.
- **Duplicate sign-up shows a form-level error** ("An account with this email already exists") above the form, which satisfies "an error shows next to the form".
- **Auth pages are signed-out only** (F017): replaces the earlier access "any" for `/sign-in` and `/sign-up`; the proxy sends a signed-in user to `/books`.

Decision 0004 records the auth-pages change; the others change no earlier decision.
